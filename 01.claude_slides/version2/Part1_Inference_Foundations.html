2 · The modelfigure: Sebastian Raschka

The architecture: a standard transformer with two kinds of attention

1The skeleton is a standard LLM

Token IDs → a 5,120-number vector each → 64 identical blocks → scores over 248K vocabulary words. Every block does two things: mix information across tokens (attention), then think about each token on its own (the FFN, which holds most of the weights).

2Full attention: exact recall, growing memory

Each new token compares itself with every past token. It can find any detail from 200K tokens ago, but it must keep every token's K and V: the KV cache, which grows with the conversation.

3Gated DeltaNet: a fixed-size memory

Instead of keeping every token, it keeps one running memory matrix. Each token writes into it (β: how strongly) and old content fades (α: how fast). It corrects what is stored rather than piling on. Same size at token 10 or 200K.

4Why 3:1

Three cheap linear layers carry the running context; every 4th full layer can still look up exact details. Linear layers scale better with context length; the full layers keep precise lookup. Result: a 4× smaller KV cache and affordable long context.

The small extras (sigmoid / SiLU output gates, QK-Norm, partial RoPE) mainly keep training stable. They don't change the memory math on the next slides.
Figure: Sebastian Raschka (Qwen3.8 27B; vision encoder and MTP head omitted), used with attribution. Intuition after Raschka's LLM architecture gallery (hybrid attention) and LLMs-from-Scratch bonus chapters on DeltaNet and gated attention.07
2 · The modelthe intuition, no maths

Linear attention: a fixed-size memory instead of a growing list

Full attention · a growing list

16 of 64 layers

Every token leaves a note about itself in a list. Each new token looks back over every note to find what matters. Nothing is forgotten, but the list keeps growing: about 0.8 GB per layer at 200K tokens.

Linear attention · one whiteboard

the other 48

Everything seen so far is summarised on one whiteboard of fixed size. Each token updates it and reads from it. It never grows: about 3 MiB per layer, at 10 tokens or 200K.

what Gated DeltaNet does with the whiteboard for every new token
1 · fadeOld writing fades a little. The model decides how much, so stale details disappear and important ones stay.
2 · checkBefore writing, it looks at what the board already says about this kind of information.
3 · correctIt writes only what is new or wrong, instead of adding another copy. This correcting is the “delta” in DeltaNet.
4 · readThe token gets its context by reading the board, not by looking back over every past token.
The trade-off: the whiteboard is cheap but blurry, the list is exact but grows. Qwen3.8 keeps 1 full-attention layer in every 4 so it can still look up exact details.
Gated DeltaNet: Yang, Kautz and Hatamizadeh, ICLR 2025. Sizes for Qwen3.8-27B. Intuition after Sebastian Raschka's LLMs-from-Scratch chapter on DeltaNet.08

Plus activations: every layer's forward outputs, kept so backward can use them. They grow with batch × sequence length and often add tens to hundreds of GB, so real runs use 8+ GPUs and split these states across them (ZeRO / FSDP). Inference keeps none of the violet rows.

Why an FP32 master copy?

Each step changes a weight by a tiny amount, e.g. 0.00001. BF16 keeps only 2–3 significant digits: just above 0.5 its next number is 0.5039. So the update rounds away and the weight never moves:

BF160.5 + 0.00001 = 0.5after 1,000 steps: 0.5 FP320.5 + 0.00001 = 0.50001after 1,000 steps: 0.51

So the optimizer updates an FP32 copy, then rounds it to BF16 for the next forward pass.

What are Adam's m and v?

Adam (the standard optimizer) keeps two running averages per weight, updated every step from that weight's gradient g:

m = 0.9·m + 0.1·gmomentum: the average direction, smooths noisy gradients v = 0.999·v + 0.001·g²variance: how big gradients usually are w −= lr · m / (√v + ε)step: big for steady weights, small for jumpy ones

Both must survive from step to step, so each is one more FP32 number per weight: +4 B and +4 B.

Mixed-precision training with Adam: 2 + 2 + 4 + 4 + 4 = 16 bytes per parameter (Rajbhandari et al., ZeRO, SC '20). BF16: 8 significant bits; FP32: 24. Adam defaults β1 = 0.9, β2 = 0.999 (Kingma & Ba, 2015). Activation memory depends on batch, sequence length and checkpointing.12

Why 16 layers? Every 4th of the 64 layers (orange) is full attention: it looks back at every past token, so it keeps each one's K and V. The other 48 are linear attention: they fold the history into a fixed ~3 MiB summary per layer. All 64 full would mean 4× the KV.

The intuition

  • Weights are a fixed cost. One copy of the model, shared by every user. Only size × precision changes it: FP8 halves it.
  • The KV cache is a notebook per conversation. Each token writes its key and value into every attention layer so later tokens can look back without recomputing. More users or longer chats mean more pages. This is the part that decides how many people you can serve.
  • Nothing else per parameter. Weights never change, so no gradients or optimizer states: 2 B instead of training's 16 B.

So how many users fit?

(72 − 55.6 − 1.5) GB ÷ 0.69 GB per user = 21 users at 8K. With FP8 weights (27.8 GB): (72 − 27.8 − 1.5) ÷ 0.69 = 61 users.

3 · Prefill vs decodethe intuition

The KV cache: work out each token's keys and values once, then reuse them

Without a cache · redo the past

writing “Time flies when you”

With a KV cache · store and reuse

same words, same answer
■ computed now  ·  ■ computed again, same numbers as last step  ·  ▢ dashed = read from the cache

Why reuse is safe

A token's keys and values depend only on that token and the ones before it. Later tokens never change them, so recomputing gives exactly the same numbers.

Why keys and values, not queries

The query is the question the newest token asks of the past. Earlier tokens already asked theirs and produced their word, so their queries are never needed again.

The price is memory

For 1,000 tokens, no cache means 500,500 key-value computations; a cache needs 1,000, but keeps them all. Qwen3.8: 64 KiB per token, 512 MiB per user at 8K.

Intuition and “Time flies” example after Sebastian Raschka, “Understanding and Coding the KV Cache in LLMs from Scratch” (2025), who measured ≈5× faster generation with a cache on a 124M model. Qwen3.8 keeps KV only in its 16 full-attention layers.16
3 · Prefill vs decodeand how the KV cache grows

Every request runs in two phases: prefill reads the prompt, decode writes the answer

Prefill · once per request

All prompt tokens go through the model together, in one pass. It writes a KV entry for every prompt token and produces the first output token. Sets TTFT.

Decode · once per output token

Only the newest token goes in. It reads every KV entry instead of recomputing the past, and adds one. Sets the gap between tokens.

Why it matters

Qwen3.8 on one H100: a 2,000-token prompt prefills in ≈ 0.23 s; a 500-token answer then takes ≈ 12 s of decode. The KV cache grows by one entry per token, per user.

Layout after a widely shared “Prefill & Decode” explainer. In Qwen3.8 only the 16 full-attention layers keep KV entries (64 KiB per token in total). Timings: first-order estimates, BF16, batch 1.17
3 · Prefill vs decodeNotebook 1: §6, §11

Why they behave so differently: prefill multiplies matrices, decode a vector

Prefill

GEMM · matrix × matrix

2,000 prompt rows share one read of W. ≈ 2,000 FLOPs per byte: the tensor cores are the bottleneck.

Decode

GEMV · vector × matrix

One row per sequence, the same W. ≈ 1 FLOP per byte: the memory bus is the bottleneck.

Same weights, same layer code. Only the number of rows changes, and that number decides whether you're waiting on math or on memory.
W is one Qwen3.8 MLP up-projection (5,120 × 17,408 × 2 B). Intensity = 2 FLOPs per multiply-add ÷ 2 bytes per weight × rows. Efficient LLM Inference §3.3; kipply (2022).18

Four numbers describe any LLM server: TTFT, TPOT, throughput, cost

latency · first impression

TTFT

Request sent → first token received. Queueing + prefill + network. Qwen3.8, 2K prompt, H100: ≈ 230 ms of prefill.

target: often ≤ 0.5–1 s for chat

TPOT / ITL

Gap between streamed tokens. TPOT is its average. 1 ÷ TPOT = tokens/s one user sees. Qwen3.8 BF16 on H100: ≈ 24 ms.

people read ~5–10 tok/s

Throughput

Tokens/s (or requests/s) summed across all users. What the finance team cares about. Goodput counts only requests that met the SLO.

rises with batch size

The L40S memory hierarchy: the closer to the cores, the smaller and faster

kernel fusion · y = silu(h + bias) × scale
The Handbook's kitchen: GPU memory (GDDR6 here) is the fridge, on-chip SRAM the counter. Fewer fridge trips = faster. FlashAttention does this for attention: tiles stay in SRAM, so the N × N score matrix never reaches GPU memory.

Why the bytes, not the math, set the pace

One token needs about 2 × 25.6B ≈ 51 GFLOPs. An H100 does that in ~52 µs. Reading 51 GB at 3.35 TB/s takes ~15 ms, about 300× longer.

Every decode step pays this read. Serving many users in the same step shares it, which is why batching matters so much.
From config shapes: linear-attention layer ≈ 0.38B params (0.77 GB), full-attention layer ≈ 0.37B (0.74 GB), LM head 1.27B (2.5 GB). The embedding table, vision encoder and MTP head are not read for a text token, so ≈ 51 GB of the 55.6 GB. H100: 989 TFLOPS BF16, 3.35 TB/s.06

E · AWS GPU instancesdecision path

Picking an AWS instance: memory first, then bandwidth

1 · Memory decides the floor

Weights + KV for your context and users + ~10% headroom. Smallest instance that fits wins on price.

2 · Bandwidth decides the speed

If ITL matters, prefer HBM (P-family) over GDDR (G-family) even when the small card fits.

3 · Splitting needs NVLink

Tensor parallel over PCIe (G-family multi-GPU) is slow. Prefer pipeline parallel there, or a P instance.

4 · Beyond one box

Over ~2 TB: multi-node, or a GB200 NVL72 UltraServer.

Usable memory = 90% of GPU memory, as vLLM's default --gpu-memory-utilization.25

The KV cache, derived one factor at a time

Qwen3.8-27B, BF16

Why K and V, not Q?

The query is only needed for the current token. Keys and values of every past token are read again at every step, so they're kept.

Query heads (24) don't count. KV heads (4) and full-attention layers (16 of 64) do: both are design choices made at training time.

How a server fills its batch: static, dynamic, continuous

same 12 requests · 4 batch slots · each box is one request, length = tokens it generates

Static · a printer

Waits for a full stack, then runs everyone until the longest finishes.

Dynamic · a bus

Leaves when full or when the timer runs out. Still waits for the longest.

Continuous · an assembly line

A finished request frees its slot at the next token step; a waiting one takes it.

vLLM, SGLang and TensorRT-LLM all batch continuously. Chunked prefill splits a long prompt across steps so running decodes don't stall.
