Introduction

Why we're spending an hour on this

Why

Training happens once. Inference runs on every request for as long as the model is live, and for most teams that's where the GPU bill ends up.

It's also closer to home than it looks. Our eval runs, LLM-as-judge passes and synthetic-data jobs are all inference workloads.

What

Inference engineering is turning a fixed set of weights into a token service that is fast enough, cheap enough and doesn't fall over.

Kiely splits the work into three layers: runtime (one model, one machine), infrastructure (many machines, regions, clouds) and tooling (what engineers actually touch).

How

One mental model first: prefill vs decode, memory vs compute. Then the toolkit every engine implements, then vLLM.

Most slides carry a number you can check. The notebook reproduces most of them on a single GPU; the § tags tell you where.

Three-layer framing: P. Kiely, Inference Engineering (Baseten, 2026), Ch. 0.

Part 1: The mental modelNotebook §4, §7

Generation is two different workloads glued together

2,000-token prompt, one forward pass
then 1 forward pass per output token
↑ first token (TTFT)

Prefill

All prompt tokens go through the model together. The weights are read once and used for thousands of tokens: large matrix–matrix multiplies, compute-bound. It writes the KV cache and decides time to first token.

Decode

Each step produces one token per sequence, and still has to read every weight plus that sequence's KV cache from HBM. Very little math per byte moved, so it's bandwidth-bound. It decides time per output token.

Nearly everything later either makes prefill cheaper (caching, chunking, disaggregation) or gets more useful tokens out of each byte decode reads (batching, quantization, speculation).

Framing follows Databricks/MosaicML, LLM Inference Performance Engineering: Best Practices (2023), and Kiely §2.4.
Part 1: The mental modelNotebook §30

A GPU is a memory hierarchy with a math unit attached

An H100 has 132 SMs, each with tensor cores and ~256 KB of on-chip SRAM. The weights don't live there. They live in 80 GB of HBM, and every decode step streams all of them through the chip.

Every step away from the tensor cores costs bandwidth, often 3–10× per step. Every trick in this talk keeps data higher up: FlashAttention keeps tiles in SRAM, quantization shrinks what crosses HBM, and offloading pushes capacity down the ladder and pays for it in speed.

Notebook §30 measures your own GPU's bandwidth and matmul rate. Expect 80–90% of spec for bandwidth and 60–80% for matmul.

NVIDIA H100 datasheet; Kiely §3 (Hardware); SRAM figure is an order-of-magnitude aggregate, not a spec-sheet number.

Four numbers describe a serving system

MetricWhat it is
TTFTRequest sent → first token back. Queueing + prefill. What makes a chat feel responsive.
TPOT / ITLAverage gap between streamed tokens. 1 / TPOT is the tokens/s one user sees.
ThroughputTokens/s (or requests/s) across everyone on the box. What finance cares about.
GoodputThroughput counting only requests that met the SLO. What you should actually optimise.
latency = TTFT + (N − 1) × TPOT

Chip Huyen's example: target TTFT ≤ 200 ms and TPOT ≤ 100 ms. Ten requests arrive and three meet both. Throughput is 10, goodput is 3.

Two more caveats from the same talk. Report P90/P99, not means. And with reasoning models, the first token generated isn't the first token the user sees.

C. Huyen, P99 CONF 2026 keynote (via The New Stack) and AI Engineering Ch. 9; goodput: Zhong et al., DistServe, OSDI '24.
Part 1: The mental modelNotebook §3, §16

Where the memory goes: weights are fixed, KV cache grows

Worked example: Llama-3.1-8B, BF16
weights 8.0B × 2 B = 16 GB KV/token 2 × 32 layers × 8 kv_heads × 128 dim × 2 B = 128 KiB one 8K-token chat = 1 GiB 64 such chats = 64 GiB

At 64 concurrent long conversations the cache is four times the weights. Concurrency × context length is what runs out first, not parameters.

Lienhart puts it the other way round for Llama-2-7B (no GQA): its ~14 GB of weights equals the KV cache for only ~28k tokens.

Part 1: The mental modelNotebook §7, §36

Decode can't keep the tensor cores busy

kipply's version of the argument: an A100 does 312 TFLOPS and moves 1.5 TB/s, so it needs about 208 FLOPs per byte to be compute-bound. The H100's ratio is 989 ÷ 3.35 ≈ 295.

A decode step does ~2 FLOPs per 2-byte weight per sequence. At batch B that's an intensity of about B. One user at a time leaves the tensor cores idle more than 99% of the time.

Batching is the fix: the same weight read serves B sequences. Drag the slider.

Reality is less tidy. Each sequence also reads its own KV cache, which batching doesn't amortise, so the real crossover comes earlier than the ridge suggests.

kipply, Transformer Inference Arithmetic (2022); H100 numbers: Kiely §2.4.1 (989 TFLOPS dense BF16, 3.35 TB/s).

Part 1: The mental modelNotebook §8

Time goes to compute, bandwidth, or overhead

Horace He's three-way split is the most useful diagnostic in this talk. Before optimising anything, work out which regime you're in, because the fixes don't transfer.

Compute

Tensor cores saturated. Long prefills, large batches.

Helps: lower precision (FP8/FP4), better kernels, more GPUs.

Bandwidth

Waiting on HBM. Decode at small or medium batch.

Helps: batching, quantization, speculative decoding, fewer bytes per useful token.

Overhead

GPU idle while Python, the scheduler or kernel launches catch up. Small models, tiny steps.

Helps: CUDA graphs, torch.compile, async scheduling.

"One way to think about compute is as a factory." (Horace He) Bandwidth is the shipping that keeps the factory supplied.
H. He, Making Deep Learning Go Brrrr From First Principles (2022). The 1.5B model in notebook §8 lands well below its bandwidth ceiling; most of that gap is overhead.

Part 2: The standard toolkitNotebook §4

The KV cache trades memory for compute

Keys and values for past tokens don't change, so we compute them once and keep them. Lienhart's summary: it turns attention from quadratic in total sequence length into linear.

The price is memory per token, per layer, per request, held for the whole life of the request. Everything else in Part 2 is some way of managing that memory.

kipply makes a nice contrarian point: at very small batch sizes you're paying for weight reads anyway, so recomputing instead of caching is closer to free than it sounds.

One layer of the cache, growing each decode step

Part 2: The standard toolkitNotebook §16

PagedAttention: give the KV cache virtual memory

Before: reserve max_len per request

Pre-vLLM systems used only 20–38% of the KV memory they reserved for actual tokens. The rest was internal and external fragmentation.

After: 16-token blocks via a block table

Blocks are allocated on demand anywhere in memory, like OS pages. Waste drops below 4%, and blocks can be shared copy-on-write across parallel samples and common prefixes.

The win isn't speed per request. It's that 2–4× more requests fit in the same memory, and continuous batching needs that headroom to do anything.

Kwon et al., Efficient Memory Management for LLM Serving with PagedAttention, SOSP 2023. Faded cells = reserved but unused.
Part 2: The standard toolkitNotebook §12

Prefix caching: pay for a shared prompt once

Solid: KV blocks found by hash, prefill skipped. Dashed: the only part that gets prefilled.

Each KV block is hashed together with everything before it. A new request that starts with the same tokens reuses the blocks and skips that prefill. vLLM V1 does this by default; SGLang's version is RadixAttention.

It pays off most for chat history, RAG over a fixed corpus, few-shot prompts and agents with long tool schemas. Notebook §12 shows cold vs warm TTFT on a 3k-token prompt.

Put static content first and dynamic content last. A timestamp at the top of the system prompt quietly turns every request into a cache miss.

vLLM docs, automatic prefix caching; Zheng et al., SGLang (RadixAttention), 2024.
Part 2: The standard toolkitNotebook §16, §38

Chunked prefill: a long prompt shouldn't stall everyone else

Without: one 16k-token prefill takes a whole step
With: prefill split to fit a per-step token budget

The knob is --max-num-batched-tokens. A smaller budget gives smoother TPOT for everyone; a larger one finishes the long prompt sooner and raises throughput. It's on by default in vLLM V1, and for small deployments it gets you much of what disaggregation promises at none of the cost.

Agrawal et al., Sarathi-Serve, OSDI '24; vLLM docs, chunked prefill.

Kernels: one fix per regime

TechniqueRegimeWhat it does
FlashAttentionbandwidthTiles Q, K, V into on-chip SRAM and computes softmax online, so the N×N score matrix never goes to HBM. Exact, not approximate. FA3 targets Hopper, FA4 Blackwell; FlashInfer and FlashMLA cover serving-specific shapes.
Kernel fusionbandwidthNorm + matmul + activation in one kernel, so intermediates stay on-chip instead of round-tripping through HBM.
CUDA graphsoverheadA decode step launches hundreds of tiny kernels. Record them once, replay as one graph, and CPU launch cost disappears.
torch.compileoverhead + bwvLLM compiles the model graph to fuse ops automatically, so new architectures get fusion without hand-written CUDA.
FP8 / FP4 GEMMscomputeLow-precision tensor cores roughly double (FP8) and redouble (FP4, Blackwell) math throughput for prefill and big batches.

For a 70B model the jump from BF16 (140 GB) to FP8 (70 GB) is the difference between two GPUs and one. That changes the deployment more than any kernel tweak.

Quantization is a quality trade, and perplexity hides regressions. Run your own task evals before and after. This is one place data scientists should own the decision, not the platform team.

Part 3: Scaling upNotebook §20

What each kind of parallelism actually splits

The communication pattern decides where each one belongs. TP talks after every layer, so it stays inside one NVLink box. PP talks once per stage, so it can cross nodes. EP sends each token wherever its experts live, so it scales with network bandwidth.

Diagram after Kiely §5.4 and the vLLM parallelism docs. Data parallel (not drawn) is simply whole copies of the model.
Part 3: Scaling upNotebook §20

Parallelism: the trade-offs in one table

StrategySplitsBuys youCosts
Tensor (TP)Each layer's matricesLower latency; fits bigger modelsAll-reduce every layer. Keep it inside an NVLink domain.
Pipeline (PP)Layers into stagesSpanning nodes cheaplyDoesn't cut single-request latency
Data (DP)Whole replicasThroughput, linearlyMemory per replica
Expert (EP)MoE experts across GPUsServing very large MoEsAll-to-all traffic, expert load imbalance

MoE changes the arithmetic

Memory follows total parameters, FLOPs follow active ones. DeepSeek-V3 is 671B total and 37B active per token; gpt-oss-120b is 117B total and about 5.1B active. Lots of memory, little compute per token.

Rule of thumb

TP inside a node, PP or EP across nodes, DP for throughput. In vLLM these are --tensor-parallel-size, --pipeline-parallel-size, --data-parallel-size and --enable-expert-parallel.

Kiely §5.4; DeepSeek-V3 Technical Report (2024); OpenAI gpt-oss model card (2025).
Part 3: Scaling upNotebook §3

Architecture choices are inference choices

Two models of similar quality can differ several-fold in KV cache per token, and therefore in users per GPU and cost per token. That decision is made at training time, usually by people who aren't paying for serving.

MHA: one K/V head per query head. GQA: groups share K/V (Llama 3 uses 8). MQA: one shared K/V head. MLA (DeepSeek): compress K/V into a small latent. Sliding-window layers cap how far back some layers look.

KV cache per token, BF16

Llama-2-7B and Llama-3.1-8B have the same 32 layers and head size; the only change is 32 vs 8 KV heads.

When you're choosing a base model to fine-tune, check num_key_value_heads in the config. It's the cheapest serving optimisation you'll ever get.

Ainslie et al., GQA (2023); DeepSeek-V2 (MLA, 2024); per-token sizes computed from the published model configs.

Disaggregation: give prefill and decode their own GPUs

Prefill pool

Compute-heavy. Builds KV caches; sized and parallelised for TTFT.
KV
KV
KV

NVLink / RDMA (NIXL)

Decode pool

Bandwidth-heavy. Streams tokens from received caches; sized for TPOT.

When it pays

Long prompts with tight SLOs on both TTFT and TPOT, at scale. DistServe reported up to 7.4× more requests, or 12.6× tighter SLOs, at the same attainment. DeepSeek serves V3/R1 this way.

When it doesn't

Small deployments and decode-heavy traffic. NVIDIA's MLSys '26 analysis finds the benefit depends on the input/output length mix. Try chunked prefill first; it's already on.

At cluster scale the KV cache also becomes something to route on. Send each request to the replica that already holds its prefix (llm-d, NVIDIA Dynamo), and spill cold blocks to CPU or SSD (LMCache).

Why separate processes

Tokenising and HTTP happen on CPU while the GPU runs, so the GPU isn't waiting on Python. That's the overhead regime again.

Picking an engine: benchmarks disagree, so run your own

Modal's LLM Engine Almanac ran about ten models across vLLM, SGLang and TensorRT-LLM at ten context lengths. Their headline: vLLM and SGLang perform comparably out of the box, so choose on other grounds, such as how fast new models and features land.

Vendor benchmarks of the same model on the same hardware routinely disagree (the vLLM and SGLang teams' DeepSeek-R1 numbers are a good example). Your prompt and output lengths matter more than anyone's leaderboard.

Part 4: vLLM in practiceNotebook §22–29

Same OpenAI API, three engines: what you actually type

vLLM

vllm serve Qwen/Qwen3-8B \ --max-model-len 32768 \ --gpu-memory-utilization 0.9 \ --kv-cache-dtype fp8

Widest model and hardware coverage. Hash-based prefix caching. The default choice.

SGLang

python -m sglang.launch_server \ --model-path Qwen/Qwen3-8B \ --context-length 32768 \ --mem-fraction-static 0.85

RadixAttention for heavy prefix reuse, a frontend with fork for multi-call programs, DP attention for big MoE.

TensorRT-LLM

trtllm-serve Qwen/Qwen3-8B \ --max_seq_len 32768 \ --kv_cache_free_gpu_memory_fraction 0.9

NVIDIA-only. PyTorch backend by default since 1.0, so no engine-build step. Best FP8/NVFP4 kernels on Hopper and Blackwell.

All three accept /v1/chat/completions, so one benchmark harness compares them fairly (notebook §26 and §29). Above them sits NVIDIA Dynamo, which orchestrates any of the three for disaggregation and KV-aware routing.

Give each engine its own virtualenv or container. They pin different PyTorch and CUDA versions, and installing two in one environment is the most common way to lose an afternoon.

docs.vllm.ai; docs.sglang.ai; nvidia.github.io/TensorRT-LLM (quick start, trtllm-serve). Flags drift between releases; check --help.

The MoE trick. Keep attention and shared layers on the GPU and push expert weights to system RAM (--n-cpu-moe). Each token touches only a few experts, so decode stays usable. Start high, lower N until you run out of memory, then step back one.

When something is slow: symptom → lever

SymptomTry, roughly in this order
TTFT too highPrefix caching and static-first prompts → shorter prompts → tune the chunked-prefill budget → more replicas or TP → disaggregate prefill
TPOT too slowFP8 or INT4 weights → speculative decoding → TP → lower max-num-seqs → a GPU with more bandwidth
Throughput too lowRaise max-num-seqs → more KV room (memory utilisation, FP8 KV) → quantize → DP replicas
OOM or preemptionsLower max-model-len → FP8 KV cache → fewer concurrent sequences → TP or a bigger GPU
Cost too highSmaller or distilled model → quantize → right-size the GPU → move offline work to batch jobs

The method matters more than the table. Write down the SLO, load-test with your prompt and output lengths, find which regime you're in, change one thing, and measure again.
