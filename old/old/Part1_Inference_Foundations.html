A · Why it mattersKiely, Inference Engineering, Ch. 0

Most of a data scientist's LLM work is already inference

An LLM project, end to end · highlighted steps run inference

It's where the money goes

Training or fine-tuning happens once. Inference runs on every request for as long as the model is live, and on every eval and judge pass you run along the way.

It sets your iteration speed

An eval over 5,000 prompts takes hours in a generate() loop and minutes in a batched engine. Anyscale measured up to 23× from batching alone.

The quality trade is yours to own

Model size, precision and decoding settings are quality decisions. Quantization can hide regressions that only your task evals catch, so the platform team can't make that call for you.

Anyscale, How continuous batching enables 23x throughput in LLM inference (2023), vs naive static batching.03

What happens when inference runs

Tokenize

Text → integer IDs. English averages roughly ¾ of a word per token; you pay per token.

Transformer layers

Each layer: attention (reads the KV cache) then an MLP. Llama-3.1-8B has 32.

Logits

One score per vocabulary entry: 128,256 numbers for Llama 3, for every new token.

Sample and stream

Pick one token, turn it back into text, send it, then feed it back in.

Why the bytes, not the math, set the pace

One token needs about 2 × 7.5B ≈ 15 GFLOPs. An H100 does that in ~15 µs. Reading 15 GB at 3.35 TB/s takes ~4.5 ms, 300× longer.

Every decode step pays this read. Serving many users in the same step shares it, which is why batching matters so much.
Per layer ≈ (8.03B − 1.05B embedding + LM head) ÷ 32 ≈ 0.22B params ≈ 0.44 GB BF16. The embedding lookup reads one row; the LM head (1.05 GB) is read in full. H100: 989 TFLOPS dense BF16, 3.35 TB/s.06

From logits to one token: temperature and top-p

Prompt: “The capital of France is” · next-token candidates (illustrative logits)
1.00 1.00

softmax(logits ÷ T)

T → 0 is greedy: always the top token. T > 1 flattens the distribution and surfaces rarer tokens.

top-p (nucleus)

Keep the smallest set of tokens whose probabilities add up to p, renormalise, sample. Greyed bars are cut.

Sampling costs almost nothing next to the forward pass, but it changes quality and reproducibility. For evals and extraction, use T = 0 or a fixed seed.

C · Prefill vs decodeNotebook 1: §6, §11

Prefill multiplies matrices; decode multiplies a vector

Prefill

GEMM · matrix × matrix

2,000 prompt rows share one read of W. ≈ 2,000 FLOPs per byte: the tensor cores are the bottleneck.

Decode

GEMV · vector × matrix

One row per sequence, the same W. ≈ 1 FLOP per byte: the memory bus is the bottleneck.

Same weights, same layer code. Only the number of rows changes, and that number decides whether you're waiting on math or on memory.
Intensity for a BF16 weight matrix: 2 FLOPs per multiply-add ÷ 2 bytes per weight × rows. kipply, Transformer Inference Arithmetic (2022).08

Input vs output tokens

Prompt tokens go through prefill, thousands per pass, so they cost far less GPU time than output tokens. That's why API price sheets charge less for input.

Worked example

Judge 50,000 rows × 400 output tokens = 20M tokens. At 2,500 tok/s that's 2.2 hours of GPU. At $4/hr, about $9.

Instance prices change often and differ by region and contract. The $/hr slider is yours to set; check the AWS pricing page.

Where you'll work

Mostly the top two layers: pick an engine, set flags, read its metrics.

Where things break

Driver ↔ CUDA ↔ PyTorch version mismatches. Use the engine's container image instead of pip-installing into a shared env.

CUDA lock-in is real: the kernels behind fast inference (FlashAttention, FP8 GEMMs) land on NVIDIA first. AMD ROCm and AWS Neuron work, with fewer options.

E · AWS GPU instancesdecision path

Picking an AWS instance: memory first, then bandwidth

1 · Memory decides the floor

Weights + KV for your context and users + ~10% headroom. Smallest instance that fits wins on price.

2 · Bandwidth decides the speed

If ITL matters, prefer HBM (P-family) over GDDR (G-family) even when the small card fits.

3 · Splitting needs NVLink

Tensor parallel over PCIe (G-family multi-GPU) is slow. Prefer pipeline parallel there, or a P instance.

4 · Beyond one box

Over ~2 TB: multi-node, or a GB200 NVL72 UltraServer.

Usable memory = 90% of GPU memory, as vLLM's default --gpu-memory-utilization.25
F · Models and memoryNotebook 1: §4

Where GPU memory goes during inference

Worked example · Llama-3.1-8B BF16 on one L40S (48 GB) · 16 users × 4K context
total = weights + KV cache + activations + runtime
weights = params × bytes/param
KV = 2 × layers × kv_heads × head_dim
     × bytes × tokens × users
runtime ≈ 1–2 GB (CUDA context, graphs)

Fixed vs growing

Weights are fixed once loaded. KV cache grows with every token of every active user. vLLM pre-allocates everything left after weights as KV blocks.

Activations during decode are small (one row per user). During a long prefill they spike, which is one reason engines cap the per-step token budget.
8.0B × 2 B = 16 GB; KV 128 KiB/token × 4,096 × 16 = 8 GiB; 48 GB × 0.9 = 43.2 GB usable.26

F · KV cacheNotebook 1: §3–4

The KV cache, derived one factor at a time

Llama-3.1-8B, BF16

Why K and V, not Q?

The query is only needed for the current token. Keys and values of every past token are read again at every step, so they're kept.

Query heads don't count. KV heads do, and that's a design choice made at training time.
Config: 32 layers, 8 KV heads, head_dim 128 (Llama-3.1-8B config.json).28

F · Dense vs MoESession 3 §3

Dense vs MoE: what one token touches

Dense

every weight, every token

Mixture of experts

router picks k of E experts

Memory follows total parameters: every expert must be resident.

Compute and bytes per token follow active parameters: attention + shared layers + k experts.

Result: big-model quality at small-model decode speed, if you have the memory.

Shazeer et al. (2017); Fedus et al., Switch Transformer (2021); DeepSeek-V3 Technical Report (2024).33
