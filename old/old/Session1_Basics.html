Part 1 · How a model generates textNotebook 1: §3

The generation loop, written by hand

out  = model(prompt_ids)                    # PREFILL: whole prompt, one pass
nxt  = out.logits[:, -1].argmax(-1)
past = out.past_key_values                 # K and V for every prompt token

for _ in range(max_new - 1):               # DECODE: one pass per token
    out = model(nxt, past_key_values=past) # feed 1 token, reuse cached K/V
    past = out.past_key_values
    nxt  = out.logits[:, -1].argmax(-1)
    seq  = torch.cat([seq, nxt], 1)

Prefill

Many tokens at once. Keeps the GPU's compute busy.

Decode

One token per pass, but still reads every weight, so it waits on memory.

FP32 KV in the CPU run uses twice that. Multiply by tokens, then by users.

Part 1 · How a model generates textNotebook 1: §6, §11

Generation is two different workloads glued together

Prefill

All prompt tokens go through together. Each weight is read once and used for thousands of tokens: matrix–matrix multiplies, compute-bound. It writes the KV cache and decides time to first token.

math units
memory bus
qualitative

Decode

Each step makes one token per sequence and still reads every weight plus that sequence's KV cache from HBM. Little math per byte moved, so it's bandwidth-bound. It decides time per output token.

math units
memory bus
qualitative
Nearly everything later either makes prefill cheaper (caching, chunking, disaggregation) or gets more useful tokens out of each byte decode reads (batching, quantization, speculation).

Part 1 · How a model generates textNotebook 1: §6

The KV cache trades memory for compute

One layer of the cache, step by step
With cache · compute 1 row
Without · recompute every row
computed this step read from memory step 1

What you pay

Memory that grows by one row per token, per layer, per user.

What you get

Each decode step computes one row of K and V instead of the whole history. Work per step stays flat instead of growing.

kipply's contrarian point: at very small batch sizes you pay for the weight reads anyway, so recomputing instead of caching is closer to free than it sounds.

Everything in session 2's Part 1 is memory management for this cache.

P. Lienhart, LLM Inference Series 3: KV caching explained (Medium, 2023); kipply, Transformer Inference Arithmetic.09
Part 1 · KV cacheNotebook 1: §3

Cache old keys and values; compute only the new row

1 Match

Score Q_new against every cached K.

2 Mix

Use the softmaxed scores to combine the cached V.

3 Append

Write K_new and V_new so the next step can read them.

The cache removes the old projections, not the scan: exact attention still reads the whole growing history every step.

Where the memory goes: weights are fixed, KV cache grows

Worked example · Llama-3.1-8B, BF16
weights   8.0B × 2 B              = 16 GB
KV/token  2 × 32 layers × 8 kv_heads
          × 128 dim × 2 B          = 128 KiB
one 8K-token chat                  = 1 GiB
64 such chats                      = 64 GiB
At 64 concurrent long conversations the cache is four times the weights. Concurrency × context length runs out first, not parameters.

Lienhart puts it the other way round for Llama-2-7B (no GQA): its ~14 GB of weights equals the KV cache for only ~28k tokens.

Part 2 · Inside the GPUNotebook 1: §5

SMs compute on tiles pulled from the memory hierarchy

HBM · 80 GB

Weights, KV cache, buffers. Large, off-die, 3.35 TB/s.

L2 cache

Shared by every SM. Tens of MB.

SM

CUDA cores and Tensor Cores, with registers, L1 and shared memory close by.

Tensor Cores accelerate matrix tiles, but useful speed also needs data reuse: a tile pulled from HBM has to be used many times.
Modular, LLM Inference Handbook · GPU architecture / memory. Die layout is schematic.15
Part 2 · GPU executionNotebook 1: §5

A kernel grid contains blocks; a block stays on one SM

Grid

All the work one kernel launch submits.

Block

Assigned to one SM for its whole life. An SM can host several blocks when registers and shared memory allow.

Warp

A scheduling group of 32 threads on NVIDIA GPUs, not 32 physical cores.

Threads are logical workers; how many stay resident depends on register and shared-memory demand.
Modular, LLM Inference Handbook · Threads, warps, blocks. Six drawn cells stand for part of a 32-thread warp.16
Part 2 · Why matrix hardware helpsNotebook 1: §5 · Notebook 2: §7

One output tile reuses the same input values many times

Each output = a row · a column

The dot product runs along the full inner dimension.

Load tiles once, reuse on chip

A 2×2 output tile reads 2 rows and 2 columns, and uses each value twice. Bigger tiles, more reuse.

Batching adds rows

More sequences = more rows of A sharing the same weight columns. That's why batching makes decode cheaper.

Local docs: Philip Kiely, Inference Engineering (2026) · §2.1, §3.1, §4.1. Conceptual 4×4 matrices; real kernels tile at several levels.17

Reuse on chip when possible. Every trip down a level costs time; kernels like FlashAttention exist to avoid them.

The ridge point

A GPU needs this many FLOPs per byte to be compute-bound. A100: 312 TF ÷ 1.5 TB/s ≈ 208. H100: 989 ÷ 3.35 ≈ 295.

Decode's intensity ≈ batch

~2 FLOPs per 2-byte weight per sequence. At batch 1 that's under 1% of peak.

Batching is the fix: the same weight read serves B sequences.

Real steps also read KV and activations, which don't amortise across the batch, so the true crossover is earlier. This is the weight-only picture.

Part 2 · The GPU underneathNotebook 1: §12

Time goes to compute, bandwidth, or overhead

Work out which regime you're in before optimising anything. The fixes don't transfer.

Compute

what the GPU's time looks like

Tensor cores saturated. Long prefills, large batches.

Helps: lower precision (FP8/FP4), better kernels, more GPUs.

Bandwidth

what the GPU's time looks like

Waiting on HBM. Decode at small or medium batch.

Helps: batching, quantization, speculative decoding: fewer bytes per useful token.

Overhead

what the GPU's time looks like

GPU idle while Python, the scheduler or kernel launches catch up. Small models, tiny steps.

Helps: CUDA graphs, torch.compile, async scheduling.

math moving bytes idle
“One way to think about compute is as a factory.” Horace He. Bandwidth is the shipping that keeps the factory supplied; overhead is the factory waiting for orders.
H. He, Making Deep Learning Go Brrrr From First Principles (2022). The 1.5B model in notebook §12 lands well below its bandwidth ceiling; most of that gap is overhead.21

Part 3 · First steps with vLLMNotebook 1: §13

Anatomy of a request inside vLLM's V1 engine

One loop iteration

Pick work within the token budget, allocate blocks, one forward pass, sample, stream out, free finished requests.

Why separate processes

Tokenising and HTTP run on CPU while the GPU runs, so the GPU isn't waiting on Python. The overhead regime again.

One scheduler for everything

Prefill and decode are both “tokens to compute”, which is why chunked prefill, prefix caching and spec decode compose cleanly.

vLLM V1 guide (docs.vllm.ai). V1 has been the only engine since v0.11 (Oct 2025); A. Gordić, Inside vLLM (2025).26
Part 3 · Inside vLLMNotebook 1: §6–16

The engine repeats schedule → execute → update

1 · Schedule

Choose requests and a token budget; allocate KV blocks before the forward pass.

2 · Execute

Run the model for the selected positions; produce candidate tokens.

3 · Update

Append accepted tokens; free completed work; stream results.

The batch, step by step
Scheduling runs at iteration boundaries, so the batch can change after every step.
Gordić, Inside vLLM (2025; engine snapshot, not a current API contract)27
